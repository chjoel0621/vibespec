## 결론

독립적으로 기대값을 정한 **92개 사례 중 88개 통과, 4개 실패**다.
실패 4개는 서로 다른 결함 4개가 아니라 **입력 타입 검증 결함 1개의 네 가지 재현값**이다.
API 미리보기와 실제 CLI `--apply`에서 모두 재현됐다. 실행 로직은 수정하지 않았다.

기존 `npm run test:journal`은 이번에도 통과했다. 따라서 기존 회귀 테스트의 통과만으로
입력 경계까지 검증됐다고 판단할 수 없으며, 이번 독립 감사가 그 빈틈을 찾아냈다.

기대값은 구현의 반환값으로 계산하지 않고 테스트 파일의 명시적인 진리표에 고정했다.
실제 파일 저장소·변경 엔진·CLI를 사용했고, 읽기 및 거절 동작 전후에는 파일 바이트의
SHA-256을 비교했다. 복구와 capture는 각각 별도 작업공간에서 검사했다.

## 핵심 판정 규칙

B는 저장된 변경 전, A는 변경 후, X는 구조상 유효하지만 저장된 전후 어느 쪽도 아닌
외부 수정이다. 두 문서 모두 실제로 변경되는 merge로 전제조건을 확인했다.

| 완료 영수증 | 두 문서 상태 | 기대 상태 | 복구 | capture |
| --- | --- | --- | --- | --- |
| 없음 | BB / BA / AB / AA | pending-write | 허용, AA로 완료 | 거절 |
| 없음 | X가 하나 이상 | external-drift, 미완료 | 거절 | 거절 |
| 있음 | AA | current | 동일 결과, 반복 실행 무변경 | 새 기록 없는 no-op |
| 있음 | AA 이외 | external-drift, 완료 | 거절 | 명시적 변경 기록 허용 |

이 규칙은 모든 조합에서 통과했다. 특히 완료된 변경을 외부에서 되돌린 것을 미완료
쓰기처럼 복구하지 않았다. 미완료 변경은 외부 수정이 섞여도 capture로 숨길 수 없었다.
거절된 복구는 원본을 덮어쓰지 않았고, 허용된 복구의 두 번째 실행은 파일을 바꾸지 않았다.

검토 만료는 부모만 변경하면 부모 검사와 부모 영향 검토가, 자식만 변경하면 자식 검사와
부모 영향 검토가 만료되는지 확인했다. 자동 검사·복구·병합 완료가 사람의 검토 항목을
닫거나 `productApproval`을 `not-assessed`에서 바꾸지 않는 것도 함께 확인했다.

## 발견한 결함 — 명시적 잘못된 대체 관계 입력이 성공 처리됨

우선순위 제안: P2, 입력 검증 및 이력 품질 결함. 이번 재현에서는 데이터 손상이나
폐기 ID 보호 우회는 관찰되지 않았다.

| replacements 입력 | 기대 결과 | API 미리보기 | CLI 적용 |
| --- | --- | --- | --- |
| 생략 / `{}` | 허용 | 허용 | 성공 |
| `false` / `0` / `""` / `null` | 객체가 아니므로 거절 | **허용** | **종료 코드 0, 새 기록 생성** |
| `[]` / `"bad"` / 유효하지 않은 ID 매핑 | 거절 | 거절 | 거절 |

이 감사의 입력 계약은 생략만 기본 빈 객체로 취급하고, 명시적인 값은 객체인지 검사한다.
`null`을 별도로 허용할 제품 계약이 필요하다면 문서화할 수 있지만, 현재의 truthiness
처리는 `false`, `0`, 빈 문자열까지 모두 똑같이 허용한다.

원인: [lifecycle-journal.mjs](../../plugins/vibespec/skills/vibespec/scripts/lib/lifecycle-journal.mjs)의
`planLifecycle`에서 타입 검증 **전에** `clone(intent.replacements || {})`를 수행한다.
따라서 falsy 값은 모두 `{}`로 변환되어 뒤의 객체 타입 검사에 통과한다.
CLI는 파일의 JSON을 정상 파싱한 뒤 이 함수를 호출하므로 같은 문제가 실제 기록까지 도달한다.

실제 CLI 재현에서는 초기 기록 1개에서 2개로 늘었고, `input.replacements`에는 원래 값이,
`replacements`에는 `{}`가 저장됐다. 모든 사례에서 기획 원본 바이트는 보존됐다.
위험은 잘못된 대체 관계 입력을 호출자가 성공으로 오인하여 필요한 추적 관계가 없는
이력을 받아들이는 것이다. 올바른 관계를 자동으로 추정하거나 보완해서는 안 된다.

수정 방향은 생략 여부와 타입 검증을 분리하는 것이다. 이번 요청은 검증이므로
실행 코드의 수정·배포·설치 캐시 반영은 하지 않았다. 실패 기대값도 완화하지 않았다.
