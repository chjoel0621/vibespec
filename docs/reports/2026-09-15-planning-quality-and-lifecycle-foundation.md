# VibeSpec 고도화 1차 구현 결과

기준일: 2026-09-15. 상태: **A 구현 및 B 평가 기반 준비, 배포 전 후보**.

## 1. 이번 작업의 결론

VibeSpec이 일회성 기획서에서 유지·고도화의 기초 자산으로 발전하려면,
문서 생성량보다 누락을 드러내고 변경 후에도 검토 맥락을 보존하는 능력을
평가해야 한다. 이번 변경은 그 첫 단계다. 장기 운영 자산으로서의 완성도나
사람의 기획 승인까지 입증한 것은 아니다.

| 구분 | 이번 상태 | 아직 입증하지 않은 것 |
| --- | --- | --- |
| A 기획 품질 | 목적별 내용 검토, 상세 누락 탐지, 안내 지침·뷰어 수정 및 회귀 검증 | 정책·예외의 완전성, 실제 구현 가능성 |
| B 유지·고도화 평가 | 3개 가상 도메인 × 6단계 재현, 검토 자료와 질문 생성 | 실제 변경의 발생 빈도, 인수인계 비용, 사람 판정 |
| Semantic 평가 | 제품 개념·KPI 중복 제거 집계 | 전체 보정 평가 완료, 사람 승인 |
| C/D/E | 이번 구현에서 제외 | 신규 관계 계약, 영속 검토 이력, 고도화 UX |

로드맵: [고도화 계획](../superpowers/specs/2026-09-15-vibespec-evolution-roadmap.md).

## 2. A: 구현한 개선

- `review-sot --purpose overview|current-state|change`를 추가했다. 생략 시
  `current-state`이며, 사용자 유형인 `--profile` 및 전체/축소 실행 모드와
  별개다. 목적은 SOT의 새 필드가 아니라 검토 문맥이다.
- 상세기능 설명·수용 기준의 공백과 일부 명백한 상투 문구를 탐지한다.
  31개 가상 상세기능의 설명과 수용 기준을 지우면 62개 누락이 나타난다.
  개요 목적에서는 이 두 종류의 공백이 정보 안내로, 나머지 목적에서는
  경고로 표시된다. 입력 SOT는 변경하지 않는다.
- 구조 PASS, 내용 검토, 선언된 KPI 측정 근거의 ready를 구분했다.
  어떤 조합도 그 자체로 제품 승인이나 개발 전달 준비 완료를 뜻하지 않는다.
- 뷰어 편집 후에는 기존 ready 안내를 숨기고 KPI별 상태도 다시 점검 필요로
  표시한다. 한국어·영어 브라우저 테스트로 확인했다.
- 생성 시 주체·조건·입력·결과·예외·검수 조건을 확인하도록 안내했다.
  모르는 정책을 검토 통과 목적으로 만들어 넣지 않는다.
- rebase의 digest 갱신과 정책 적합성 검토, 기능 병합과 기획 전체 통합을
  각각 구분하도록 워크플로 지침을 보완했다.

자동 검토는 보수적인 누락·문구 검사다. 긴 문장이라고 완전한 명세인 것도
아니고, 경고 0이라고 정책 충돌이 없는 것도 아니다. `current-state`와
`change`는 이번 자동 규칙의 강도가 같고 작성·검토 문맥이 다르다.

## 3. 기존 데모에서 새롭게 드러난 공백

전체 회귀 검증의 첫 실행은 기존 `demo-tree`의 “모든 데모 경고 0” 가정에서
실패했다. 파일을 직접 확인한 결과 새 규칙이 실제 빈 필드를 찾은 것이었다.

| 데모 | 언어별 누락 | KO/EN 산출물 합계 |
| --- | --- | --- |
| flea-market 본문 | 수용 기준 14개 | 28개 |
| flea-market escrow | 수용 기준 2개 | 4개 |
| flea-market offer | 수용 기준 3개 | 6개 |
| meeting-room-booking 본문 | 설명 20개 + 수용 기준 20개 | 80개 |
| 합계 | 4종 문서 | 8개 산출물, 118개 경고 |

기존 데모 원본은 수정하지 않았다. 테스트는 이 공백의 정확한 코드·경로·
경고 수준을 명시적으로 대조한다. 새 공백도 실패하고 기존 공백을 실제로
해소해도 기대값 검토가 필요하다. 이는 결함 승인이나 경고 숨김이 아니다.
118개는 번역본을 포함한 문서별 경고 수이며 독립 제품 문제 수가 아니다.

## 4. B: 유지·고도화 평가 기반

[실행 방법과 한계](../../evaluation/lifecycle/README.md),
[사례 정의](../../evaluation/lifecycle/cases.mjs),
[실제 엔진 재현](../../evaluation/lifecycle/replay.mjs).

캠페인 동의, 회의실 예약, CRM 내보내기의 가상 정책으로 각각 다음을 재현했다.

`기능 추가 → 부모 정책 변경 → rebase → merge → 폐기 → 동일 ID 재도입`

초기 문서와 사례 정의의 digest를 고정하고, 단계마다 입력 계획·예상 영향·
관찰 결과·전후 digest·스냅샷을 보존했다. 관련 없는 요구사항과 화면의
보존도 검사한다. 동일 실행 반복은 개념 수나 전이 수에 중복 집계하지 않는다.

3개 개념·18개 전이가 재현됐다. 다음 네 가지는 후속 검토 후보다.

| 관찰 | 후속 설계 질문 |
| --- | --- |
| 부모 정책 변경 후 추가 기획에 이전 정책이 남음 | 어떤 정책 관계를 기계적으로 추적할 필요가 있는가? |
| rebase 후 최신 digest와 이전 정책 문구가 공존 | 내용 검토 여부를 digest와 어떻게 분리할 것인가? |
| merge 후 정책·KPI 수동 검토가 남음 | 검토 잔여 항목과 기준선 통합 완료를 어떻게 추적할 것인가? |
| 폐기한 ID가 다시 추가되고 폐기 이유는 최종 SOT에 없음 | 폐기 이력·대체 관계·ID 재사용 방지는 어디에 보존할 것인가? |

세 도메인은 같은 변경 패턴을 공유하는 의도적인 스트레스 사례다.
독립적인 실제 운영 사례에서 이 문제가 반복된다는 증거로 해석하면 안 된다.
정책 충돌 관찰은 이 사례의 content reviewer 결과에 한정되며, 모든
워크플로나 AI의 자연어 판단이 충돌을 발견하지 못한다는 주장은 아니다.

로컬 검토 패킷: `outputs/vibespec-lifecycle-evaluation-2026-09-15/`.
`report.json`과 도메인별 초기 상태·6개 단계·사람 검토 질문, 총 25개 파일이다.
`--write`는 새 폴더만 허용하며 기존 증거를 덮어쓰지 않는다.

사람 검토는 모두 pending이다. 검토자·검토 대상 digest·확인한 문제와 오탐·
놓친 문제·소요 시간·인수인계 가능성을 실제로 기록해야 한다.
현 실행기는 승인 증빙을 읽어 판정하는 기능이 없으므로 질문 파일을 작성해도
자동 승인으로 전환되지 않는다. 생성 품질·오탐률·미탐률·저작 부담·
인수인계 시간은 not-assessed로 남는다.

## 5. Semantic 평가 집계 정정

기존 11개 manifest에 `conceptId`를 추가했다. 고정된 원본·overlay·판정 자료는
변경하지 않았다. 기존 산출물 집계는 유지하고 별도 고유 집계를 추가했다.

| 평가 단위 | 현재 | 목표 |
| --- | --- | --- |
| natural/controlled 제품 개념 | 2 | 8 |
| 고유 측정 KPI | 5 | 30 |
| 측정 방식 | 2: event-ratio, external | 5 |

WeekChef KO/EN과 같은 반복은 같은 개념·KPI ID로 묶는다. 같은 KPI ID의
측정 방식이 다르면 집계 오류로 실패한다. ID가 실제 같은 KPI 개념을
뜻하는지는 사례 작성자가 보장해야 한다. legacy와 미승인 baseline 후보는
제외한다. 이번 가상 lifecycle 사례도 이 수치에 더하지 않는다.

이 집계는 산출물 범위의 수량 검사다. 승인 증빙 검증과 사람 보정 평가는
미구현이며, 수량 목표를 채워도 승인으로 전환되지 않는다.

## 6. 검증 기록

- RED → GREEN: 31개 빈 상세기능, KO/EN 뷰어 범위·stale 안내,
  lifecycle 재현 함수, Semantic 중복 제거 집계.
- `npm run check:all`: exit 0. 저장소 경로·문서 링크 검사, 빌드,
  SOT/c14n/변경 계획/rebase/merge/평가/패키징 회귀 및 7개 브라우저
  테스트 스크립트를 포함한다.
- lifecycle 저장 검사: 새 검토 패킷 생성, 기존 패킷 덮어쓰기 거절 및
  기존 파일 보존을 확인했다.
- 범용 skill-creator 검사기는 로컬 Python에 PyYAML이 없어 실행되지
  않았다. 새 의존성을 설치하지 않고 기존 plugin-contract 및 호스트
  런타임 계약 검사 결과를 사용했다. 범용 검사기 통과를 주장하지 않는다.
- 변경 전 HEAD와 현재 지침으로 각각 1회, 동일한 3개 상태 보고 요청을
  독립 에이전트에 적용했다. 양쪽 모두 미검토 상태를 승인으로 표현하지
  않았다. 이 소규모 점검에서는 행동 개선 효과가 입증되지 않았다.
  실제 플러그인 실행·신규 기획 생성이나 반복 호스트 비교를 대체하지 않는다.

지침 검토는 `skill-creator`의 범위 보존과 `writing-skills`의 행동 검증
원칙을 사용했다. 코드는 회귀 결과로, 지침 적용은 제한된 시나리오 관찰로
구분해 보고하며 인과적인 품질 향상으로 과장하지 않는다.

## 7. 다음 단계와 배포 경계

1. 사람이 세 lifecycle 검토 패킷을 판정하고 사례의 현실성부터 검토한다.
2. 실제 유지·고도화에서 발생한 추가 사례와 변경 이력을 확보해 패턴 편향을
   줄이고, 인수인계와 재검토 비용을 측정한다.
3. 독립적인 사례에 근거해 C의 최소 관계 계약과 D의 영속 검토 이력 범위를
   정한다. 이번 가상 반복만으로 새 스키마를 확정하지 않는다.
4. Semantic 보정 평가의 남은 개념·KPI·측정 방식과 승인 증빙을 채운다.
5. 릴리스 버전·변경 로그를 준비하고, 변경된 런타임으로 실제 Claude/Codex
   호스트 수용 검증을 다시 수행한 다음 배포한다.

이번 작업은 저장소 내 후보 구현이다. 플러그인 버전은 0.17.2로 유지했고
설치 캐시 교체·배포·커밋·푸시는 하지 않았다. 테스트의 호스트 검증 통과는
변경된 후보에 대한 실제 양쪽 호스트 릴리스 승인을 의미하지 않는다.
