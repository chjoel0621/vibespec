# VibeSpec 고도화 로드맵: 신뢰할 수 있는 지속 운영 기획 자산

작성일: 2026-09-15

분석 기준: 플러그인 0.17.2

상태: 검토용 제안. 단계별 출시 범위이며, 구현 승인·완료를 의미하지 않는다.

## 1. 목표

VibeSpec에서 만든 기획이 최초 구축 이후에도 기능 추가, 정책 변경, 출시, 폐기, 담당자 교체 과정에서 신뢰할 수 있는 서비스 기준선으로 유지되도록 한다.

두 성과를 함께 추구한다.

1. 기획 품질: 사용자 행동, 조건, 결과, 주요 예외를 이해할 수 있고 누락을 찾을 수 있다.
2. 자산 지속성: 무엇이 현재 유효하고, 왜 바뀌었으며, 무엇을 재검토해야 하는지 추적할 수 있다.

전체 기획 완성도를 근거 없는 단일 백분율로 표시하지 않는다. 실제로 검사한 항목과 확인하지 못한 항목을 분리해서 전달한다.

## 2. 근거와 기존 계획의 관계

2026-09-15 분석에서 확인한 사실:

- 생성 지침은 사용자 여정에서 화면을 도출하고 주요 분기·루프를 작성하도록 안내한다.
- 구조 검증과 내용 리뷰는 서로 다른 검사다. 내용 리뷰의 설명 길이·모호성 검사는 제한적이며 상세기능 설명·수용 기준 누락을 충분히 검사하지 않는다.
- 비공개 서비스 SOT의 메모리 복제본에서 상세기능 31개의 설명·수용 기준을 비우고 기능 설명·수용 기준을 일반 문장으로 바꿔도 구조 PASS, 리뷰 경고 0건, 측정 ready였다. 실제 원본 파일은 변경하지 않았다. 서비스 식별 정보와 원본 산출물은 공개하지 않는다.
- 측정 ready는 선언된 KPI 측정 근거에 대한 결과다. 기획 전체의 승인·전달 준비도를 보장하지 않는다.
- 현재 전체/축소 모드는 런타임 기능 구분이며 기획 상세도 구분이 아니다.
- 변경 계획은 ID·digest·변경 경로를 검증한다. 추가 기획·재기준·병합·영향 분석 기반이 있다.
- rebase는 부모 digest를 갱신한다. 정책 변경에 따른 내용의 적합성을 자동 확인하지 않는다.
- merge는 기능·화면·flow와 inScope를 반영한다. 다른 PRD·KPI·의미 내용은 수동 검토 항목으로 남긴다.
- 뷰어 실행 취소 이력은 메모리에 있다. 영속 이력은 저장한 파일, change-plan/receipt, Git 등의 별도 보존 경로가 필요하다.
- Semantic 평가 실행은 3개 평가 산출물·7개 KPI·2종 측정 방식·2개 라벨 오류를 보고했다. 번역본은 독립 제품으로 계산하면 안 된다.

[기존 calibration sprint](2026-08-10-semantic-assurance-calibration-sprint-design.md)의 독립 제품 개념 집계, 사람 평가, 8개 제품·30개 KPI·5종 방식 목표를 계승한다. 이 로드맵은 해당 평가를 대체하지 않으며 반복 변경과 인수인계 평가를 추가한다.

## 3. 접근 대안과 권고

| 대안 | 장점 | 비용·한계 | 판단 |
|---|---|---|---|
| 생성 지침과 리뷰만 강화 | 빠르게 개선하고 기존 파일 호환 유지 | 정책 의존성과 장기 변경 의미를 구조적으로 관리하기 어려움 | 첫 단계로 수행 |
| 검증 보강 후 선택적 기획 계약과 변경 검토 추가 | 기존 강점을 보존하며 장기 운영을 지원 | 스키마·수정기·뷰어·병합의 공동 설계 필요 | 권고 |
| 계정·승인·실시간 협업 중심 플랫폼으로 확대 | 조직 단위 협업 지원 가능 | 플러그인보다 큰 서비스 운영·보안·비용 범위 | 이번 범위 제외 |

## 4. 제품 원칙과 범위

### 유지할 원칙

- JSON은 제품 사실과 결정의 기준 데이터이며 HTML은 같은 데이터의 표시·편집 결과다.
- 기존 파일 열기·저장만으로 새 계약이나 사람의 검토·승인 상태를 부여하지 않는다.
- 정책·수치·운영 상태를 AI가 추정한 경우 사실 확인과 구분한다.
- 현재 ID, 명시적 변경 계획, dry-run, 적용 영수증을 보존한다.
- 자동 검사와 사람/AI의 의미 검토를 구분한다. 자동 PASS가 검토자의 판단을 대체하지 않는다.
- 새 필드의 값이 미확인인 경우 unknown 또는 검토 필요 상태를 유지한다.
- 플러그인의 로컬 파일 중심 동작과 자동 네트워크 전송 없음 원칙을 유지한다.

### 포함 범위

- 목적별 기획 생성 지침과 내용 누락 검사.
- 정책·결정·행동 조건·출처를 연결할 선택적 계약의 검증과 도입.
- 기준선의 용도 및 확인 상태, 변경 검토, 병합 후 잔여 작업, 폐기·대체 이력.
- 기존 CLI, 뷰어, 추가 기획 흐름 안에서 동일한 검토 상태 표시.
- 반복 변경과 인수인계의 재현 가능한 평가.

### 제외 범위

- 서비스 소스 자동 구현, API/DB 전체 명세 생성 의무화.
- 운영 DB나 배포 환경에 대한 자동 연결·동기화.
- 계정·실시간 공동 편집·중앙 승인 서버·법적 서명 시스템.
- 모든 자연어 모순의 자동 판정 보장.
- 기존 예제와 사용자 파일의 일괄 강제 마이그레이션.

## 5. 목표 사용자 경험

기획 작성 → 누락·미결정 검토 → 기준선 지정 → 추가 기획 작성 → 변경 영향 검토 → 내용 조정 → 구현/출시 근거 확인 → 병합 및 잔여 검토 → 기준선 갱신 → 다음 변경.

사용자가 항상 답을 찾을 수 있어야 하는 질문:

1. 현재 서비스에 적용되는 기획은 무엇인가?
2. 검토 중인 제안과 운영 중인 기능은 어떻게 다른가?
3. 이 정책은 왜 결정됐고 어떤 기능이 의존하는가?
4. 이번 변경으로 어디를 다시 확인해야 하는가?
5. 병합 후 무엇이 아직 미반영·미검토 상태인가?
6. 이 기능을 폐기했다면 대체 기능과 이전 결정은 어디에 있는가?

## 6. 단계별 출시 계획

각 단계는 독립적으로 검토·출시 가능한 단위다. 달력 일정과 버전 번호는 구현 범위를 확정한 뒤 정한다. 기존 문서의 0.17.3/0.18 표기는 후보 구분이며 이 문서가 버전을 배정하지 않는다.

### 단계 A — 검사 결과의 의미와 최소 기획 품질 정리

목표: 빈 상세 명세가 조용히 통과하는 문제와 검증 결과의 과대 해석을 줄인다.

산출물:

- 구조 정합성, 내용 리뷰, KPI 측정 정의를 분리한 지침·출력 문구.
- 상세기능의 빈 설명·빈 수용 기준 탐지. 문서 목적과 예외 사유를 함께 다뤄 의도적인 개요를 구현 불가 오류로 취급하지 않는다.
- 장문 일반 표현에 대한 보수적 advisory와 구체적 개선 질문. 글자 수를 품질 점수로 사용하지 않는다.
- 서비스 개요, 현행 서비스 기획, 상세 변경 기획의 작성 기준. 전체/축소 런타임 모드와 명확히 구분한다.
- 상세 변경 기획에서 주체·전제·입력·정상 결과·주요 예외·검수 기준을 확인하는 작성 지침. 초기에는 기존 desc/acceptance를 활용한다.

완료 기준:

- 앞서 재현한 31개 상세기능 공백이 내용 리뷰에 노출된다.
- 구조 PASS와 측정 ready만으로 전체 전달 준비 완료라고 표시하지 않는다.
- 정상적인 짧은 개요와 해당 없는 예외를 불필요하게 차단하지 않는다.
- 기존 SOT의 읽기·저장·임베딩과 계약 없는 문서의 not-assessed 동작을 보존한다.

주요 위치: `references/workflows/create.md`, `common.md`, `scripts/lib/content-review.mjs`, `tests/content-review.test.mjs`, 필요 시 `src/js/56-semantic.js`.

### 단계 B — 지속 운영 평가 기반 확보

목표: 어떤 구조가 실제로 부족한지 반복 변경으로 입증한다.

산출물:

- 기존 Semantic calibration의 독립 제품·KPI 집계와 사람 평가 기록.
- 별도 lifecycle 평가 세트: 최초 기획부터 최소 5회 변경을 적용한 이력, 원본·변경 계획·예상 영향·결과·검토 기록.
- 엔진 검사 품질, AI 생성 품질, 장기 자산 유지 품질의 별도 보고서.
- 새로운 계약 후보마다 기존 desc/acceptance/K/E/D로 해결 가능한지 비교한 근거.

초기 대상: 캠페인 협업 서비스, 예약 서비스, CRM의 3개 독립 개념. 실제 서비스 자료는 로컬 분석에만 사용하고 공개 fixture는 합성·익명화·공개 승인된 자료로 마련한다.

완료 기준:

- 3개 제품 각각 최초 기획 + 최소 5회 변경을 기록한다.
- 정상 변경, 정책 충돌, 미검토 재기준, 병합 잔여 검토, 폐기 기능 재도입 사례를 포함한다.
- 번역본·반복 실행을 독립 제품 수에 중복 집계하지 않는다.
- 확인된 누락과 오탐을 사람 평가와 연결한다. 사람이 검토하지 않은 결과는 후보로 남긴다.
- 기존 Semantic 평가의 미달 항목을 그대로 보고하고 lifecycle 수치로 대체하지 않는다.

주요 위치: `evaluation/semantic-assurance/`, 제안 경로 `evaluation/lifecycle/`. 평가 메타데이터는 제품 SOT에 혼입하지 않는다.

### 단계 C — 선택적 기획 계약과 안정 참조 확장

착수 조건: B에서 같은 누락 관계가 최소 3개 독립 제품에서 반복되고 기존 구조만으로 관리하기 어렵다는 근거가 있을 것. A의 명백한 누락 검사는 이 조건을 기다리지 않는다.

목표: 중요한 기획 관계를 중복 문장에서 참조 가능한 자산으로 전환한다.

후보 개념:

- 행동 계약: 실행 주체, 전제, 입력 조건, 결과, 주요 예외.
- 공유 정책: 정책 내용, 적용 기능, 유효 범위, 변경 이유.
- 결정: 질문, 선택한 답, 이유, 영향 대상, 대체된 결정. 기존 D#와 의미가 겹치는 별도 체계를 무심코 추가하지 않는다.
- 근거: 입력 문서·코드 버전·확인 날짜·검토 유형. 파일 해시는 내용의 동일성을 증명하며 실제 배포 여부나 설명의 진실성을 증명하지 않는다.
- 수명주기: 현행·제안·폐기와 대체 관계. 기존 todo/doing/done과 다른 차원으로 정의한다.

계약 결정 산출물:

- 신규 SOT 버전 또는 선택적 계약 버전 방식의 호환성 비교와 결정 기록.
- 상세기능 F#:index의 append/마지막 삭제 제약을 유지할지, 영속 상세기능 ID·별칭 매핑으로 확장할지 결정.
- 삭제·병합 시 참조 승계와 ID 재사용 방지 방법. scope별 로컬 ID 재번호와 장기 식별성의 관계를 명시.
- 정책·출처 등 제품 데이터와 검토 영수증 등 운영 메타데이터의 저장 위치 확정.

완료 기준:

- 하나의 공통 정책을 참조한 모든 관련 기능을 조회할 수 있다.
- AI가 제안한 사실과 검토자가 확인한 사실을 구분한다.
- 미확인 운영 상태가 done 등의 값만으로 운영 확인 완료가 되지 않는다.
- JSON Schema, typed change-plan, query, diff, merge/remap, viewer round-trip, migration이 같은 계약을 따른다.
- 지원하지 않는 버전은 명시적으로 거부하며 저장 중 새 필드를 조용히 잃지 않는다.

주요 위치: `references/sot.schema.json`, `sot-schema.md`, `scripts/validate-sot.mjs`, `scripts/lib/{change-plan,sot-query,diff,merge,semantic-reference-registry}.mjs`, `src/js/20-state.js`, 상세 편집·IO 모듈 및 대응 테스트.

### 단계 D — 변경 검토와 기준선 갱신의 완료성

목표: 최신 해시와 검토 완료를 구분하고, 기획 통합 이후 남은 일을 추적한다.

산출물:

- 이전 기준선 스냅샷 또는 접근 가능한 이전 버전과 현재 기준선의 비교.
- 명시적 참조에 따른 영향 목록, 미검토 항목, 영향 없음 판단과 이유를 기록하는 검토 결과.
- 검토 결과를 before/after digest, 영향 대상, 검토 주체·종류에 결합. 사람 검토라고 기록하려면 실제 사람의 판단 근거가 필요하다.
- 기준선이 다시 바뀌면 관련 검토를 stale로 표시한다. 이전 스냅샷이 없으면 영향 검토 불가로 남기며 빈 변경 목록을 만들지 않는다.
- rebase의 구조적 갱신 상태와 내용 검토 상태를 분리한다. 최신 해시만으로 승인·배포 상태로 승격하지 않는다.
- merge 후 PRD·KPI·정책·사용자 여정의 수동 검토 항목을 영속 작업으로 기록. 반영 완료/해당 없음과 이유를 남긴다.
- 기준선의 기획 승인·구현 확인·운영 확인을 별도 사실로 표시. 파일 digest와 릴리스 근거를 연결하되 배포를 자동 추정하지 않는다.
- 기능 폐기·대체 기록 및 과거 ID를 통한 이력 조회.

완료 기준:

- 동의 링크 발급 조건 변경 후 과거 정책을 따르는 추가 기획은 rebase만으로 검토 완료가 되지 않는다.
- 병합으로 기능이 추가돼도 미반영 정책·KPI가 있으면 잔여 항목이 표시된다.
- 재기준·검토·병합·기준선 갱신을 각각 재실행해도 이력과 결과가 모순되지 않는다.
- 다중 파일 쓰기 중 실패하면 중간 상태를 명시하고 일관된 복구 경로를 제공한다.
- 폐기된 기능의 재도입은 관련 이력 검토 대상으로 나타난다.

주요 위치: `scripts/lib/{rebase,merge,tree,diff}.mjs`, 해당 CLI, `references/workflows/{rebase,merge,workspace}.md`, 신규 검토 기록 모듈·테스트.

### 단계 E — 운영 조망·인수인계 경험과 출시 검증

목표: 기획 파일을 처음 보는 사람도 현재 상태와 다음 검토 작업을 이해한다.

산출물:

- 현재 기준선, 추가 기획, 검토 필요, 병합 잔여 항목, 폐기 이력을 연결한 뷰어 탐색.
- 기능별 정책·결정 이유·출처·변경 이력 조회.
- 현재 SOT와 보존한 이력에서 파생한 인수인계 요약. 별도 진실 원본을 만들지 않는다.
- Git 사용 예시와 Git 없는 파일 스냅샷·검토 영수증 보존 방법.
- 기존 CLI와 뷰어가 같은 의미의 상태를 보여주는 일관성 검증.

완료 기준:

- 이전 대화가 없는 검토자가 현재 정책, 변경 이유, 미출시 제안, 미검토 항목, 폐기 대안을 모두 찾는다. 정답 여부와 소요 시간을 기록한다.
- 브라우저 재시작 후에도 저장한 결정·변경 검토·기준선 이력을 복구할 수 있다.
- 원본 변경 이후 파생 보고서는 최신 결과처럼 표시되지 않는다.
- 패키징된 플러그인을 Claude와 Codex에서 각각 설치해 실제 생성·변경 여정을 검증한다.

주요 위치: `src/js/{30-history,40-io,45-file-connection,56-semantic,65-detail,87-map}.js`, `scripts/workspace.mjs`, 브라우저 테스트, `docs/{workflows,architecture,development,releasing}.md`.

## 7. 의존성과 첫 출시 범위

- A는 즉시 상세화할 수 있다. B의 평가 설계도 A와 함께 시작할 수 있다.
- C는 B의 반복 근거와 계약 결정을 통과한 관계만 채택한다.
- D의 검토 절차 설계는 B에서 검증하며, 정책 수준의 영향 추적 구현은 C에 의존한다.
- E의 최종 상태 표시는 C·D의 계약에 의존한다. 각 단계에 필요한 최소 UI는 해당 단계에서 함께 제공한다.

첫 출시 범위는 A와 B의 평가 실행 기반이다. C~E 전체를 하나의 구현 작업으로 묶지 않는다. 첫 구현 계획은 단계 A만 대상으로 작성한다.

## 8. 반복 변경 평가와 제안 통과 기준

아래 기준은 목표이며 현재 달성 주장이나 대규모 정확도 주장이 아니다.

| 시나리오 | 확인할 결과 |
|---|---|
| 새 기능 추가 | 관련 없는 기획 항목·ID·참조 보존 |
| 공통 정책 변경 | 라벨이 붙은 명시적 의존성의 영향 목록 누락 없음 |
| 서로 다른 추가 기획의 전제 충돌 | 확인된 충돌 또는 미검토 상태가 노출됨 |
| 내용 조정 없는 rebase | 내용 검토·승인으로 자동 승격되지 않음 |
| 병합 후 정책·KPI 미반영 | 잔여 검토가 영속적으로 남음 |
| 기능 폐기·대체 | 과거 참조와 대체 이유를 찾을 수 있음 |
| 실제 코드와 기획 차이 | 입력 근거로 확인 가능한 차이와 미확인 영역을 분리 |
| 기존 버전 파일 열기·저장 | 허용된 migration 외 무관한 데이터 변화 없음 |
| 담당자 인수인계 | 사전 정답표의 5개 핵심 질문에 모두 답함 |

정량 기록:

- 의미 있는 무관 항목 손실, 검토 없이 완료로 승격된 사례: 평가 세트에서 0건.
- 라벨이 붙은 명시적 의존성 누락: 평가 세트에서 0건. 자연어 전체의 완전한 탐지를 의미하지 않는다.
- 사람 확인 blocker 오탐: 평가 세트에서 0건. 일반성 없는 패턴은 advisory로 조정한다.
- 반복 변경 중 필요한 사람 수정 수, 판단에 걸린 시간, 재검토량, 추가 필드 작성량: 변경 단계별 실측.
- Claude/Codex 고정 입력 결과는 같은 기준으로 비교하며 반복 실행을 제품 수에 합산하지 않는다.
- 실패·재시도·미검토 결과를 삭제하거나 성공 사례로 치환하지 않는다.

## 9. 호환성과 복구

1. 단계 A/B는 원칙적으로 기존 SOT 계약을 유지한다.
2. C는 계약 버전과 reader 지원 범위를 먼저 결정하고 viewer·CLI·package를 함께 배포한다.
3. 기존 파일 자동 승격 금지. 명시적 migration은 새 파일을 만들고 전후 diff와 검증 결과를 제공한다.
4. `sot-c14n-v1`의 기존 의미를 조용히 바꾸지 않는다. 변경이 필요하면 별도 canonicalization 계약으로 다룬다.
5. 새 필드 도입 시 normalize/save, change-plan, query, diff, remap, merge, embed 경로의 보존성을 검증한다.
6. 검토 보고서의 유효성은 입력 digest와 결합한다. 수정 후 오래된 보고서로 준비도를 표시하지 않는다.
7. 새 버전 사용 중 실패하면 보존한 원본·스냅샷으로 돌아갈 수 있어야 한다. 새 데이터를 구버전 형식으로 조용히 삭제하지 않는다.
8. 제품 이력은 SOT에 필요한 결정과 관계를 저장하고, 검토 로그·스냅샷은 제품 폴더의 명시적 기록으로 보존한다. 정확한 레이아웃은 C의 계약 결정에 포함한다.

## 10. 출시별 확인과 역할

- 제품 판단 담당자: 실제 정책, 기준선의 용도, 의미 충돌, 해당 없음 사유와 인수인계 정답을 확인한다.
- 구현 담당자/AI: 계약·도구·뷰어·테스트를 구현하고 검토 근거를 제출한다. 사람 판단을 대신 기록하지 않는다.
- 검토 담당자: 기존 판단과 독립적으로 누락·오탐·데이터 보존을 확인한다. 소규모 팀에서 역할을 겸해도 검토 대상과 시점은 남긴다.

단계 완료 시 해당 규칙 테스트와 계약 테스트를 실행한다. viewer 변경에는 브라우저 회귀, 데이터 계약 변경에는 migration·round-trip·merge 검증을 포함한다. 실제 배포 전에는 기존 `npm run check:all`과 양쪽 호스트의 버전·bundle digest가 일치하는 acceptance 절차를 유지한다.

## 11. 다음 결정과 실행 경계

이번 문서의 권고: 로컬 플러그인 기반을 유지하고 A → B → 근거가 확보된 C → D → E 순서로 진행한다.

지금 확정할 범위는 단계 A/B의 우선순위다. 새 계약의 필드명·상태 enum·영수증 포맷·버전 번호는 평가 근거와 함께 C의 설계에서 확정한다. 이것들은 미구현 동작을 사실처럼 문서화하지 않기 위한 명시적인 후속 결정이다.

로드맵 검토 후 첫 구현 계획은 단계 A의 파일별 변경, 테스트 사례, CLI/뷰어 문구, 호환성 확인으로 한정한다. 기능 구현·커밋·배포는 이번 로드맵 작성에 포함하지 않는다.
